# Agent guidance

## Project

This repository contains `wakil`, a local-first Python CLI agent for working with a personal Markdown knowledge base.

`wakil` is designed for one user working locally on knowledge work, not coding automation. The target knowledge base is GBrain / Obsidian style: Markdown files, links, concepts, notes, meeting transcripts, web clippings, source material, journal entries, and synthesis documents.

The goal is to help the user ingest, search, connect, revise, and reason over a Markdown knowledge base.

The project thesis is:

> Build a local, git-native knowledge-work agent that helps a single user discover useful connections, maintain a Markdown knowledge base, and turn raw inputs into durable, searchable memory.

The engineering principle is:

> Keep the implementation simple unless added complexity has a clear and self-evident impact on the target use case.

Do not over-engineer this project.

## Repository Map

Before assuming a design question is undecided or that some behavior is
untested tribal knowledge, check these first:

- **`docs/adr/*.md`** — every accepted architectural/design decision (search
  ordering, git-landing semantics, entity schema, MCP tool design, etc.) is
  recorded here. `status: accepted` means the decision was made, not
  necessarily that every consequence of it landed in code — grep for the
  actual implementation before citing an ADR as current behavior.
  - **`docs/adr/0000-template.md`** - example template for future ADRs
- **`docs/DEVELOPMENT.md`** — recurring dev patterns worth generalizing
  (mandatory reading; see Working Agreement item 13 below).
- **`docs/TROUBLESHOOTING.md`** — a dated, append-only log of real bugs and
  gotchas that cost debugging time (mandatory reading; see item 13 below).
- **`README.md`** — user-facing command reference and workflow walkthroughs.
- **`CHANGELOG.md`** — auto-generated by the release workflow from commit
  messages (via `git-cliff`, see `cliff.toml`); don't hand-edit it.
- **`skills/`** (repo root) and **`src/wakil/skills/`** — the former are
  outer-agent skills read over MCP (e.g. `mcp-coordinator`); the latter are
  DAG-internal skills (`skills/<source-type>/SKILL.md`) loaded by
  `wakil enrich`'s own pipeline. Don't confuse the two when asked to edit
  "a skill."

## Dev Workflow

```bash
uv sync                  # install deps
uv run pytest            # unit + integration tests
uv run pytest -m eval    # live-model skill evals (needs a provider key; skipped otherwise)
uv run ruff check        # lint
uv run ty check          # type-check (uvx ty check if ty isn't installed locally — CI runs this too)
```

Commits are gitmoji-prefixed Conventional Commits (e.g. `♻️ refactor(ingest):
...`, `✨ feat(cli): ...`) — the `commit` skill applies the right emoji/type
per change; `git-cliff` (`cliff.toml`) parses this format to group the
changelog by type (feat/fix/perf/refactor/docs; chore/build/ci/test/style are
grouped but excluded from the version-bump decision). Releases are cut via
the `Release` GitHub Actions workflow (`workflow_dispatch`, choose
`patch`/`minor`/`major`) — see recent commit history since the last tag to
judge the right bump: new backward-compatible functionality is `minor`, pure
fixes/refactors are `patch`, anything breaking an existing CLI command or MCP
tool contract is `major`.

## Prime Directive

Build the smallest useful version of `wakil` that advances the local knowledge-work use case.

Before adding abstraction, ask:

```question
Does this clearly improve local Markdown knowledge work for one user?
```

If the answer is not obviously yes, do not add it.

Prefer simple, explicit, boring Python code over clever frameworks or speculative architecture.

## Design Biases

Prefer:

```text
simple local workflows
Markdown as source of truth
SQLite as operational store
QMD as first-class search
git-native changes
clear memory lifecycle
human review
rich CLI output
grounded citations
explicit commands
small composable services
```

Avoid:

```text
remote runtimes
complex permissions
large agent frameworks
hidden background behavior
automatic rewriting without review
multi-agent orchestration
premature graph databases
opaque memory systems
overly abstract plugin architectures
hosted product assumptions
```

Concrete instances of the above, called out explicitly so they aren't
individually re-litigated as "reasonable" additions (carried forward from
the project's original planning doc):

```text
coding-agent workflows (this is a knowledge-work tool, not a coding assistant)
Slack/email gateways
browser automation framework
desktop or mobile app
complex distributed job system
fine-tuning
marketplace
enterprise permissions
cloud-first architecture
```

## Working Agreement for Agents

When contributing to this repo:

1. Keep changes small.
2. Do not add speculative abstractions.
3. Preserve the local-first CLI focus.
4. Prefer Markdown, SQLite, QMD, and Git over new infrastructure.
5. Avoid building for multi-user or hosted deployment yet.
6. Keep model behavior behind deterministic application controls.
7. Add tests for meaningful behavior.
8. Update docs when behavior changes.
9. Respect the distinction between raw sources, durable notes, and memory.
10. Treat sensitive content carefully.
11. Show reviewable diffs for knowledge-base modifications — a pre-write
    preview for direct CLI/tool use, or the resulting pull request for an
    agent following the `mcp-coordinator` skill over MCP (docs/adr/0019).
    Both satisfy this item; it does not mean every write must block on a
    human immediately before it happens, in every context.
12. Do not silently rewrite user knowledge.
13. **Mandatory every run that does substantive work (not a trivial
    read-only question):** read `docs/DEVELOPMENT.md` and
    `docs/TROUBLESHOOTING.md` before starting — they exist precisely so a
    fresh session doesn't re-debug or re-decide something already settled.
    Before finishing (and always before a `commit`), apply the
    `development-docs` skill's judgment process to decide whether anything
    from the session belongs in either file — a recurring pattern worth
    generalizing goes in `DEVELOPMENT.md`; a real bug that cost debugging
    time, wasn't obvious from the code, and could plausibly recur goes in
    `TROUBLESHOOTING.md`. The default answer is "no, nothing qualifies" —
    most sessions should add nothing to either file, and padding them with
    routine work is itself a violation of this item. Every entry that is
    added must cite a concrete source (commit SHA, PR #, or session detail).

The project should feel like a careful local knowledge assistant, not a sprawling agent platform.

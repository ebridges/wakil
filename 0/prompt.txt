## 0. Grounding corrections (read this before the rest)

**wakil already implements most of the `ingest-source` workflow as code, for three source shapes.** `wakil ingest {transcript,text,article} [--branch/--commit/--pr]` (`src/wakil/cli/main.py:401-442`) captures a raw source; `wakil enrich &lt;source_id&gt; [--branch/--commit/--pr]` (`main.py:289-376`, `src/wakil/app/ingest_service.py`) runs the second stage — model-driven synthesis (`prepare_enrichment`), entity resolution against existing notes (`_run_entity_resolution`), schema-routed stub-page construction (`_build_stub_entities`, keyed off `schema.directory`), and a hard invariant gate (`validate_proposal`: dedup paths, schema-validate every proposed file, hard-stop on unknown entity types) before anything is written. This is precisely the two-stage raw→enrich pattern `quickcapture-ingest` modeled loosely in prose, now real and code-enforced. **Consequence:** for the three CLI-native shapes, `content-synthesis` / `entity-resolution` / `entity-enrichment` / `note-routing` / `note-conformance` should mostly document *how to drive `wakil ingest` → `wakil enrich`* and how to triage its output, not re-derive synthesis/resolution judgment from scratch. The prose value concentrates on (a) source types the CLI can't ingest natively yet — PDF, YouTube, voice memo, archive-mining, Kindle/Readwise/social-post — which need normalizing down to text/article/transcript + a rich `--context` string before the CLI takes over, and (b) work that never touches the CLI at all (note-revision on existing notes, cross-note concept-synthesis, ad hoc entity work during a manual edit).

**`kb-commit`'s message convention must not be the source corpus's type→emoji taxonomy.** wakil already has a fixed convention baked into code: `wakil &lt;kind&gt;: &lt;description&gt;`, `kind ∈ {ingest, note, link, memory, dream, source, chore}` (`COMMIT_PREFIXES` / `commit_message()` in `src/wakil/app/git_service.py:22,37-40`). ## 4. Execution phasing

Dependency graph, not arbitrary batching — several skills need to *name* other skills correctly, so authoring order matters for avoiding dangling `related_skills` (issue #8):

**Phase 0 — foundational reads (no output, informs everything else):** `conventions/quality.md`, `_output-rules.md`, `RESOLVER.md`/`schema.md` (source), `entity-resolve/SKILL.md`, `article|text|transcript/SKILL.md`, `git_service.py`, `schema_migrate_service.py`, `ingest_service.py`. These are the files every downstream skill must not contradict.

**Phase 1 — repository governance (no dependencies on other new skills):** `note-routing`, `note-conformance`. These are referenced by nearly everything else (routing/schema decisions show up in ingestion, entity work, and revision), so they should exist and be stable before anything names them.

**Phase 2 — knowledge transformation, foundational-first:** `knowledge-query` before `knowledge-research` (research explicitly builds on and cites query, per skill-refactor.md's own "typical research workflow" diagram) → `entity-resolution` before `entity-enrichment` (same dependency, stated explicitly in the source doc) → `note-revision` (depends on note-conformance/note-routing being final for its "update in place" guidance, and conceptually follows knowledge-query/research per the doc's diagram) → `content-synthesis` → `source-ingestion` (source-ingestion's per-type sections should be written last within this phase since they're the biggest fan-in and benefit from content-synthesis's boundary being settled — what does source-ingestion normalize to vs. what does content-synthesis interpret).

**Phase 3 — workflow orchestration:** `ingest-source` last among the transformation-layer skills, since it must literally name the six skills in its pipeline diagram — writing it before they exist (or before their names/boundaries are final) is exactly how the dangling-reference problem recurs.

**Phase 4 — system operation:** `skill-authoring` and `kb-commit` can run in parallel with each other and largely independent of phases 1-3 (they're about the *system*, not KB content) — but `skill-authoring` should do a final pass after phase 3 to write its "how the 12 skills relate" example content against the real, finished set, and `kb-commit` benefits from `note-conformance` being final (it references schema-migrate triage).

**Phase 5 — cross-skill consistency pass (mandatory, not optional):** one pass across all twelve for dangling `related_skills`, terminology drift (e.g. "entity page" vs. "entity note," "source note" vs. "raw source"), and verifying every code reference (`wakil enrich`, `schema migrate`, `slugify()`, `COMMIT_PREFIXES`, etc.) is accurate against current source, not just plausible.

## 5. Execution mechanism

Recommend a **single Workflow, but not a single flat fan-out** — structure it to match the phasing above, because the dependency chain is real (not cosmetic): several skills materially need to read finished sibling skills before they can correctly reference them, and running all 12 as independent parallel agents from a shared brief risks each one independently inventing slightly different phrasing for the same shared concepts (notability gate, State/Timeline distinction, citation format) — recreating issue #7 (citation drift) and the general "un-cross-referenced standards" problem inside the *new* catalog, not just failing to fix it in the old one.

Concretely:
- One agent (or a short serial sequence) for Phase 0 + Phase 1, since these are foundational and small in count (2 skills) but referenced everywhere — get them right and stable first.
- Parallel per-skill authoring agents *within* Phase 2, but each handed the finished Phase 0/1 output plus a shared "glossary" excerpt (terminology + the exact wording of cross-cutting principles — notability gate, Iron Law of exact phrasing, State-vs-Timeline, source precedence) pinned in every agent's brief, not left to each agent's independent judgment. This is the direct mitigation for risk (c) in your framing (cross-skill inconsistency).

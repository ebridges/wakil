## 1. `search_workspace` and how `query` is used

**Signature** (`src/wakil/app/search_service.py:33`):
```python
def search_workspace(
    session: Session,
    config: WorkspaceConfig,
    query: str,
    limit: int = 10,
    mode: str = "search",
) -&gt; list[SearchHit]:
```
It queries three engines and concatenates results: QMD (if `config.qmd_enabled`), then SQLite FTS5 over notes/memories/sources (deduping notes already found by QMD via `seen_notes`).

**QMD path** (`src/wakil/integrations/qmd.py:66`, `qmd_search`): the entire `query` string is passed as a single CLI argument to the external `qmd` binary:
```python
subprocess.run(["qmd", mode, query, "--json", "-n", str(limit)], ...)
```
Default `mode="search"` is QMD's BM25 keyword mode (module docstring: "`search` (BM25 keyword), `vsearch` (vector similarity), `query` (hybrid with LLM re-ranking)"). So this is exactly a bag-of-words BM25 query — however qmd itself tokenizes the raw string.

**FTS5 path** (`src/wakil/storage/fts.py`): `search_notes`/`search_memories`/`search_sources` all funnel through `_search()`, which calls `to_match_expression(query)`:
```python
def to_match_expression(query: str) -&gt; str:
    tokens = re.findall(r"[A-Za-z0-9_]+", query)
    return " OR ".join(f'"{token}"' for token in tokens)
```
This is explicitly bag-of-words: every alphanumeric token in `query` is OR'd together, so bm25 ranking is computed over the union of all tokens present anywhere in the (potentially huge) blob — a single rare/topical word from `title` gets diluted by hundreds of tokens pulled in from an expanded `@file:` context block. There's no query-length cap or truncation anywhere in this path before it hits `re.findall`.

**`RELATED_NOTE_LIMIT`**: defined in `src/wakil/app/ingest_service.py:70` as `RELATED_NOTE_LIMIT = 5`. It caps the number of *hits returned/kept* (passed as `limit=` into `search_workspace`, which forwards it as `-n` to qmd and `LIMIT :limit` to the FTS SQL) — it does not cap query size at all.

**Actual frontmatter writer**: `_transcript_metadata()` (`src/wakil/app/ingest_service.py:1457`) builds the dict actually written:
```python
def _transcript_metadata(config, proposal, created):
    values = {
        "created": created,
        "meeting_date": proposal.meeting_date,
        "title": proposal.title,
        "origin_kind": proposal.source_type,
        "file_url": f"file:{proposal.origin}",
        "context": proposal.context,
    }
    template = transcript_frontmatter_template(config)
    if template is None:
        return {"created": created, "meeting_date": proposal.meeting_date}
    metadata = {}
    for key, template_value in template.items():
        normalized = _KNOWN_FIELD_VALUES.get(key.lower().replace("-", "_"))
        filled = values.get(normalized) if normalized else None
        metadata[key] = filled if filled is not None else template_value
    return metadata
```
It's driven by `_KNOWN_FIELD_VALUES` — a hardcoded map of template-key aliases to known value sources (`created`, `meeting_date`, `title`, `origin_kind`, `file_url`, `context`). There is **no** `description`/`abstract` entry in `_KNOWN_FIELD_VALUES`, so even if a KB's `SCHEMA.md` template declared a `description` field for transcripts, `_build_raw_file`/`_transcript_metadata` has no source value to fill it with today — it'd fall through to `template_value` (the template's literal placeholder). Adding an abstract would require both the `source.yaml` sub-schema entry *and* a new `_KNOWN_FIELD_VALUES` mapping + a `values[...]` entry in `_transcript_metadata` fed by whatever computes the abstract.

`_build_raw_file` itself (line 1423) is the actual frontmatter-template/file-writer function (not `_stub_content`, which is a different helper used for entity-resolution stub pages, `src/wakil/app/ingest_service.py:963`, unrelated to sources).

## 3. Eval design

**File location: `src/wakil/skills/builtin/&lt;name&gt;/eval.json`, one file per skill.** Not a parallel `evals/` tree. Reasoning, grounded in wakil's own conventions:
- `skill-authoring`'s "Extend vs. create" section (76-84) already establishes the exact pattern of skill-scoped support files sitting beside `SKILL.md` — `references/`, `templates/`, `scripts/`. An eval file is a fourth instance of the same pattern, not a new one: colocated, versioned with the skill it tests, naturally kept in sync during editing (evaluation-driven development wants "identify gap → build scenario → iterate" as a tight loop against the file you're actively editing).
- `tests/` is reserved for wakil's *own code* (`test_skill_loader.py`, `test_skills_resolver.py`, `test_skills_cli.py`) — these evals are about *skill-content quality*, a different axis, and mixing them into `tests/fixtures/` would blur that line the project already draws cleanly.
- One JSON file (not one-file-per-scenario) keeps "12 skills → 12 new files" instead of "12 skills → 36+ new files," matching the "don't build more than 12 skills need" instruction.

**Shape**, adapted from the doc's `{"skills": [...], "query": "...", "files": [...], "expected_behavior": [...]}`:

```json
{
  "skill": "kb-commit",
  "scenarios": [
    {
      "id": "group-unrelated-edits-into-separate-commits",
      "related_skills": [],
      "query": "I edited jane-doe.md to add a new role, and separately fixed a typo in acme-corp.md. Commit these.",
      "workspace": {
        "base_fixture": "tests/fixtures/kb",
        "overlay": {
          "people/jane-doe.md": "---\ntype: person\nname: Jane Doe\n...",
          "companies/acme-corp.md": "---\ntype: company\nname: Acme Corp\n..."
        }
      },
      "expected_behavior": [
        "Proposes at least two separate commit groups, not one combined commit",
        "Uses the `wakil &lt;kind&gt;: &lt;description&gt;` message form with kind in {ingest,note,link,memory,dream,source,chore}",
        "Uses `note` as the kind for both edits (manual edits to existing notes)",
        "States it will inspect each diff individually before grouping (not `git add -A`)",
        "Explicitly asks for confirmation before running `git commit`",
        "States it will not push unless explicitly asked"
      ]
    }
  ]
}
```

Field-by-field adaptation:
- `skills` → `related_skills` (defaults to just the file's own skill; only populate for scenarios that deliberately test a handoff, e.g. a `content-synthesis` scenario that should mention handing off to `entity-resolution` by name).
- `files` → `workspace.base_fixture` (reuse `tests/fixtures/kb`, which already has `SCHEMA.md`, `people/jane-doe.md`, `meetings/`, `concepts/`, `drafts/`, `sources/transcripts/`) plus `workspace.overlay` (scenario-specific starting state, written on top). This mirrors the existing `kb_path` fixture in `tests/conftest.py` (copy fixture KB into `tmp_path`) rather than inventing a new fixture mechanism.
- `expected_behavior` → same name, same purpose (a rubric, not a diff), but each item should be one of these five kinds, specific to a markdown-editing/judgment skill rather than a code-generation one:
  1. **Correct CLI-command citation** — did it name the actual command (`wakil schema migrate`, `wakil skills validate`, `wakil git summary`) rather than inventing one or describing a hand-rolled procedure the code already owns?
  2. **Correct terminology/convention usage** — `wikilink` form `[[path]]` not `../relative`, `State`/`Timeline` not invented section names, `wakil &lt;kind&gt;: ...` commit form, `COMMIT_PREFIXES` membership.
  3. **Correct handoff naming** — does it name the right sibling skill by its exact directory name for further action, and not invent a 13th skill or misname one?
  4. **Anti-pattern avoidance** — does it *not* clobber Timeline, *not* auto-merge an ambiguous entity, *not* guess a directory, *not* fabricate a citation? (Negative assertions matter as much as positive ones for these skills — several are explicitly designed around "never do X.")
  5. **Preview/confirm discipline** — for any skill whose procedure mandates a preview-before-write step (`note-revision`, `kb-commit`), does the response actually surface a diff/plan and ask before claiming to write?

**Minimum 3 scenarios per skill** (per the doc's checklist item), chosen per-skill to hit: (a) the skill's core happy path, (b) its stated ambiguous/no-match/conflict case (every one of the 12 has one — that's exactly where these skills' judgment is load-bearing), (c) a handoff-boundary case (does it correctly *stop* and defer to a sibling rather than overreaching). Representative picks beyond kb-commit above:
- `note-revision`: a scenario that reproduces the documented "clobbering bug" shape (three related pages, one new transcript) — `expected_behavior` checks it does NOT regenerate the whole page and DOES flag "my new version is shorter" as a stop signal.
- `entity-resolution`: an ambiguous two-candidate case — `expected_behavior` checks it returns "ambiguous," not a forced match, and does not auto-merge.
- `note-routing`: a case with no `RESOLVER.md` in the overlay workspace — `expected_behavior` checks it stops and asks rather than guessing a directory.

**Loading/validation:** a small Pydantic model, `EvalScenario`/`EvalFile`, under `src/wakil/skills/evals.py` (sibling to `resolver.py`, `models.py`), used both by the runner (§4) and by a lint check (§5a) that every builtin skill has an `eval.json` with ≥3 scenarios and well-formed `expected_behavior` (non-empty strings).

## 4. Eval runner design

**Location:** `tests/evals/` — a pytest-based runner, not a standalone `scripts/` CLI. Reasoning: pytest already gives collection, parametrization, `-k`/`-m` filtering, and reporting for free; wrapping that machinery in a hand-rolled script would be exactly the "speculative abstraction" CLAUDE.md warns against for a 12-skill, single-developer tool. Concretely:

- `tests/evals/runner.py` — support module, no test collection itself:
  - `load_scenarios(skill_name) -&gt; list[EvalScenario]` — reads `src/wakil/skills/builtin/&lt;name&gt;/eval.json` via the `evals.py` Pydantic model.
  - `materialize_workspace(tmp_path, scenario) -&gt; Path` — `shutil.copytree(FIXTURE_KB, target)` (same as `tests/conftest.py`'s `kb_path` fixture) then writes `scenario.workspace.overlay` files on top.
  - `run_scenario(client, skill: Skill, scenario, workspace: Path) -&gt; str` — builds a system prompt the same shape as `wakil.llm.skill_loader.build_system_prompt` (wakil identity + skill body), but instead of a JSON-contract schema, the "contract" is just: respond as the agent would, describing what you'd do and why. User prompt = `scenario.query` + a serialized listing of the overlay files' paths and contents (since this is a single-shot completion, not real tool use — see tradeoff note below).
  - `grade_transcript(client, scenario, transcript: str) -&gt; GradeResult` — second `client.complete()` call: system = "You are grading an AI agent's response against a rubric. For each item, answer pass/fail with a one-sentence reason." user = `expected_behavior` list + the transcript. Parse a small JSON array of `{item, pass, reason}` (reusing the existing `validate_model_response`-style strict-JSON parsing pattern from `wakil.llm.schemas`, not a new ad hoc parser).
- `tests/evals/test_skill_evals.py` — the actual pytest test, parametrized over all 12 skill names × their scenarios, each test:
  1. `pytest.skip("no model provider configured")` if `resolve_client()` returns `None` (graceful no-key local behavior, matching `test_llm_client.py`'s own null-config test).
  2. Runs `run_scenario`, then `grade_transcript`.
  3. Asserts every rubric item passed; on failure, prints the failing item + transcript excerpt for a human to read (pytest's own `-q` failure output is enough; no custom reporter needed).
  4. Marked `@pytest.mark.eval` (see §5b).

**Explicit design tradeoff, named rather than hidden:** this runner does single-shot transcript grading (skill prose + query → model's described response → graded), not full agentic execution against real files via tool use. A true "spin up Claude Code with the skill loaded and actual file-editing tools" harness would be strictly more faithful but is a materially larger piece of infrastructure (sandboxing, tool-call loop, real filesystem mutation review) that 12 skills don't justify per CLAUDE.md's minimalism directive. The doc's own evaluation-scenario JSON shape (`query`/`files`/`expected_behavior`) doesn't mandate real tool execution either — it's compatible with grading a described response. Recommend transcript grading as the right-sized choice; flag this tradeoff explicitly in the runner's module docstring so a future reader doesn't mistake it for full agentic verification.

**Model choice:** default to whatever `resolve_client()` already resolves (respects `WAKIL_PROVIDER`/`WAKIL_MODEL`, no new config surface). Don't build a Haiku/Sonnet/Opus sweep into the routine runner — that's real API cost multiplied by 3 for no benefit on every run. Instead, support it as an opt-in via the existing `WAKIL_MODEL` env var (a contributor can re-run `uv run pytest -m eval` three times with three different `WAKIL_MODEL` values to satisfy the doc's "tested with Haiku/Sonnet/Opus" checklist item during actual skill-authoring work, without the routine harness needing to know about all three).

## 5. CI wiring recommendation

Confirming your proposed split — it's correct — with exact changes:

### (a) Fast, free, deterministic skill lint — extends the blocking `pytest -q` gate, zero `ci.yml` changes

- New module `src/wakil/skills/lint.py`: pure functions operating on a resolved skill's text (no model calls, no network). Checks:
  - line count (warn/fail thresholds well below the doc's 500-line ceiling — e.g. fail &gt;500, matching the doc exactly);
  - TOC presence for any `references/*.md` over 100 lines (a heading-scan for a leading list of `##` links);
  - frontmatter shape/description length (extends what `resolve_skill`/`_load_skill` in `src/wakil/skills/resolver.py` already validates structurally — this lint reuses that same parse, just adds content-quality checks on top rather than duplicating name/skill_api/readability checks that already exist);
  - a short deny-list of self-referential time-sensitive phrases (`"as of this writing"`, `"as of now"`, `"as of today"`) — mechanically catchable, exactly the `kb-commit` case found in §1;
  - dangling cross-references: regex-extract skill names mentioned in backticks/prose and check each against `discover_skill_names()`'s real output (catches the `skill-authoring` hardcoded-list drift risk noted in §1, and generalizes it to all 12);
  - presence of a `references/*.md` file that nothing in `SKILL.md` points to (dead weight, per `skill-authoring`'s own stated rule).
- Wire it into the existing `skills_app` command family as `wakil skills lint` (extends the space `wakil skills validate` already occupies, doesn't duplicate its structural checks) — human/agent-usable ad hoc during authoring.
- Wire it into CI for free via `tests/unit/test_skill_lint.py`: parametrize over the 12 builtin skills, call the same `lint.py` functions, assert zero findings. This is picked up by the existing `uv run pytest -q` step with **no `ci.yml` edits at all** — it's just more unit tests, deterministic, no network, no secrets, matching the "structural/mechanical lint fits the existing philosophy fine as a blocking check" framing.

### (b) Live-model evals — separate, non-blocking, opt-in

- `pyproject.toml` — register the marker and change default collection:
  ```toml
  [tool.pytest.ini_options]
  testpaths = ["tests"]
  markers = ["eval: live-model skill evaluations (real API calls; excluded by default, run with -m eval)"]
  addopts = "-m 'not eval'"
  ```
  This is the only `pyproject.toml` change needed. `ci.yml`'s `uv run pytest -q` stays **byte-for-byte unchanged** and remains zero-network/zero-secret by construction — `addopts` does the exclusion centrally rather than requiring every CI step to remember `-m "not eval"`.
- New optional workflow `.github/workflows/skill-evals.yml`, `workflow_dispatch`-only (no `push`/`pull_request` trigger, and explicitly no `schedule:` — recurring unsolicited API spend is exactly the "hidden background behavior" CLAUDE.md warns against for a single-developer local-first tool):
  ```yaml
  name: Skill Evals
  on:
    workflow_dispatch: {}
  jobs:
    evals:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v7
        - uses: astral-sh/setup-uv@v8.3.2
          with: { enable-cache: true, python-version: "3.12" }
        - run: uv sync --locked
        - run: uv run pytest -m eval -q
          env:
            ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
            NO_COLOR: "1"
  ```
  Requires a repo secret only configured if/when the user chooses to run it manually — the default zero-secret CI posture is untouched.
- Local usage: `uv run pytest -m eval` (or `-m eval -k kb_commit` for one skill), using whatever provider env var is already set; gracefully skips (not fails) when unset, per `resolve_client() -&gt; None`.
- **Docs:** add a short "Skill evaluations" subsection to README's existing `## Development` section (next to the two existing `pytest`/`ruff` lines) documenting `uv run pytest -m eval`. Add one sentence to `docs/skill-refactor.md`'s `skill-authoring` section, where it currently says a future `skill-evaluation` skill "is not required for the first release" — note that this evaluation mechanism (`eval.json` + `tests/evals/` + `wakil skills lint`) now fulfills that deferred intention as tooling rather than a 13th skill, so a future reader doesn't wonder why no `skill-evaluation` skill was ever added.

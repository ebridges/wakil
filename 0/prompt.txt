**`src/wakil/app/memory_service.py:98-106`** — `retrieval_rank()` currently takes `(state, created_at)` and returns a single float. Extend its signature to accept confidence and fold it in as a fractional sub-rank within the same integer-valued state bucket, so state ordering is never disturbed:
```python
def retrieval_rank(state: str, created_at: datetime | None, confidence: float | None = None) -&gt; float:
    """Lower ranks first. Encodes the fading rules described above.

    `confidence` only breaks ties *within* the same state bucket — it is
    added as a fractional offset (0.0-1.0, higher confidence = lower
    offset) on top of the integer state rank, so it can never move a memory
    across a state boundary (e.g. a low-confidence durable memory still
    outranks every candidate memory).
    """
    rank = _STATE_RANK.get(state, 2.0)
    if state == "working" and created_at is not None:
        created = created_at if created_at.tzinfo else created_at.replace(tzinfo=UTC)
        age_days = (datetime.now(UTC) - created).days
        if age_days &gt; WORKING_FADE_DAYS:
            rank = _FADED_WORKING_RANK
    effective_confidence = confidence if confidence is not None else _DEFAULT_CONFIDENCE
    return rank + (1.0 - effective_confidence) * _CONFIDENCE_SPREAD
```
with two new module constants near `_STATE_RANK` (line 36):
```python
_DEFAULT_CONFIDENCE = 0.5  # tiebreak for NULL confidence — see open question below
_CONFIDENCE_SPREAD = 0.5   # keeps the offset &lt; the 1.0 gap between adjacent _STATE_RANK values
```
`_CONFIDENCE_SPREAD` must stay `&lt; 1.0` (the smallest gap between any two `_STATE_RANK` values, e.g. `durable=0.0` to `candidate=1.0`) — this is the mechanism that guarantees confidence is strictly a same-state tiebreak, never a cross-state override. `0.5` gives headroom.

## Open Questions for the User

1. **NULL-confidence tiebreak default (flagged, not decided).** I used `_DEFAULT_CONFIDENCE = 0.5` (mid-point/neutral) in the `retrieval_rank()` sort-key change in item 4. Reasoning: most existing rows have `confidence IS NULL` (it was write-only before this change), and treating unknown-confidence as "average" avoids two bad outcomes — (a) defaulting NULL to `1.0`/high would rank every historical fact ahead of any explicitly-low-confidence opinion for the wrong reason (absence of a signal isn't the same as a strong signal), and (b) defaulting NULL to `0.0`/low would bury the entire pre-existing corpus behind newly-confidence-tagged memories on day one of this change, which is a much bigger, more surprising behavior shift than "new low-confidence opinions rank slightly behind." But this is a real, debatable product choice with no objectively correct answer — please confirm `0.5`, or state a preferred alternative (e.g., treat NULL as if unset and don't apply any confidence tiebreak until confidence is populated, which is close to today's behavior for existing data).

2. **`≤0.4` confidence guidance: prompt-only or enforced?** The plan treats "guidance ≤0.4 for hot takes" as pure prompt text with no code-level enforcement or warning (matches the proposal doc's own framing and today's precedent — `_clamp01()` already silently accepts anything in `[0,1]`). Should there be a warning/log (not a hard failure) when the extractor tags something the prompt describes as a hot-take pattern with a higher confidence, or is prompt guidance alone acceptable for phase 1? I did not build any such check — flag if you want one.

3. **`opinion` guidance scope: transcript-only vs. all extraction skills.** The agreed scope names only `prompts.py` + `transcript/SKILL.md`. But `article/SKILL.md:14-17` already has closely related (narrower) guidance about fact vs. inference/hypothesis, and `text/SKILL.md` has none. All three skills produce the same `CandidateMemoryModel` via the same shared `build_extraction_prompt`. My plan puts the *generic* fact-vs-opinion rule into `prompts.py` (so it reaches article/text/transcript alike) but the *low-confidence hot-take register* rule only into `transcript/SKILL.md` (matching the proposal's "1:1 conversation" framing, which is transcript-specific). Confirm this split is what you want, versus adding the hot-take-register bullet to `article`/`text` too, versus keeping literally everything transcript-only and nothing in `prompts.py`.

4. **ADR number/filename and date.** No draft ADR exists yet (confirmed: only `docs/memory-opinion-and-register.md` is untracked; `git log --all` has no `0013` reference), so `0013` is uncontested today — but this repo has many open branches (`docs/resolver-md-migration-strategy`, `feat/wire-skill-resolver-into-ingest`, etc.), and ADR numbering is manual/sequential (not auto-assigned), so a race with another in-flight PR claiming `0013` first is possible between now and merge. Also: I used `date: 2026-07-22` (today) — confirm, since ADR 0004 in this repo omits `date` entirely, unlike every other ADR, so there's no single universal template rule to follow.

5. **`SearchHit` doesn't carry `confidence`.** `search_service.py:16-24`'s `SearchHit` dataclass exposes `state` for memory hits but not `confidence`, even though ranking will now use it. This doesn't block the ranking change (the sort happens before `SearchHit` construction, inside `_ranked_memory_hits`), but it does mean a test/CLI consumer can't assert "hit X had confidence Y" without re-querying — the test in item 7b will have to assert ordering by identity (title/ref) rather than by an inspectable confidence value on the hit. Do you want `confidence: float | None = None` added to `SearchHit` for debuggability/display, or is ordering-only sufficient for phase 1? (I did not add it, to stay minimal per CLAUDE.md's stated bias.)

6. **`_CONFIDENCE_SPREAD` magnitude.** I chose `0.5` (half the `1.0` gap between adjacent `_STATE_RANK` values) so confidence differences are visible but can never cross a state boundary. This is an arbitrary but safe choice — no strong reason it couldn't be `0.9` or `0.1` instead; smaller values make confidence a weaker tiebreak. Flagging as a tunable, not a considered/tested constant.

7. **`docs/entity-model.md`** (not in the agreed 9 items) also documents `memory_type='event'`/`'question'` as examples (lines 131-132, 191) but doesn't enumerate the full type list, so it doesn't strictly need an `opinion` mention — leaving it untouched unless you want it kept in lockstep with the README.

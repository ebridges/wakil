```python
def _candidate_entity_notes(
    session,
    workspace_id: int,
    text: str,
    schemas: dict,
    *,
    extra_terms: set[str] = frozenset(),
) -&gt; list[tuple[str, str]]:
    """Direct title lookup for proper nouns against known entity directories.

    Complements (does not replace) the relevance search above: a name match
    here doesn't depend on QMD/FTS ranking a short, sparse entity stub above
    longer notes that merely mention the same name.

    extra_terms: additional lowercase candidate words (e.g. from
    _title_terms) that bypass the capitalized-proper-noun requirement —
    for text sources where casing can't be trusted as a name signal.
    """
    directories = tuple(
        f"{schema.directory}/"
        for schema in schemas.values()
        if schema.directory and schema.category in ("identity", "hybrid")
    )
    if not directories:
        return []
    candidates = {
        phrase
        for phrase in _PROPER_NOUN_RE.findall(text)
        if len(phrase) &gt; 2 and phrase not in _PROPER_NOUN_STOPWORDS
    }
    # candidates ends up including a lot of irrelevant terms -- e.g. small talk,
    # speech terms (e.g. Mm-hmm, Very, etc.): is there a way to filter those out?
    candidates |= extra_terms
    if not candidates:
        return []
    notes = session.scalars(
        select(Note).where(
            Note.workspace_id == workspace_id,
            or_(*(Note.path.like(f"{d}%") for d in directories)),
        )
    )
    matches: list[tuple[str, str]] = []
    for note in notes:
        note_title = note.title or ""
        if not note_title:
            continue
        if any(
            phrase.lower() in note_title.lower() or note_title.lower() in phrase.lower()
            for phrase in candidates
        ):
            matches.append((note.path, note_title))
    return matches
```

    if not related_notes:
        return "(none found)"

**Answer to the precise question**: Neither is it literal verbatim insertion of the candidate list into the prompt, nor is it a pre-filter on which notes get *loaded/fetched from disk* (full note content is never loaded here at all — only `note.path`/`note.title` are queried from the DB, and `snippet=""` is hardcoded). It's a third, more indirect path:

- The regex candidates only ever act as a matching key against existing `Note.title` values already in the SQL result set (all notes under `identity`/`hybrid`-category entity directories, loaded via one `Note.path.like(...)` query, line 556-561).
- If a junk candidate (e.g. "Mm-hmm", "Very", "Right") happens to substring-match (or be substring-matched by) some real note's title, that note's `(path, title)` — just the wikilink + title string, one line — gets appended to `related_notes`/`related_pairs`, which *does* land verbatim in both the extraction prompt and the resolution prompt as one extra `- [[path]] title` line.
- If no note title collides with the junk candidate, it causes **zero** prompt bloat — it's silently dropped. So actual context bloat only manifests as accidental extra "- [[path]] title" lines when a filler word happens to coincide with an existing note title/substring (e.g., a short entity stub whose title is itself a common word).

So "bloating the context" here is real but indirect and probabilistic — driven by false-positive substring matches against real note titles, not by the raw regex-candidate list itself ever being serialized into a prompt.

## 3. What the regex actually matches on real text

```python
_PROPER_NOUN_RE = re.compile(
    r"\b[A-Z][A-Za-z0-9&amp;.'-]*(?:\s+[A-Z][A-Za-z0-9&amp;.'-]*){0,3}\b"
)
```

This matches any run of 1–4 whitespace-separated capitalized "words" (each starting with `[A-Z]`, continuing with letters/digits/`&amp;`/`.`/`'`/`-`). It has **no notion of proper-noun-ness** beyond capitalization — it will match:
- Legitimate names: "Mosaic", "Ian Gutwinski", "Riviera Partners"
- Sentence-initial capitalized common words/interjections: "Mm-hmm" (hyphen is an allowed continuation char, so it matches as one token), "Very", "Right", "Yeah" — though "Yeah" is explicitly stopword-listed already (see below), "Very" and "Right" and "Mm-hmm" are not.

This exact gap is called out in the code's own inline comment (line 551–552, quoted above), i.e. the maintainers already flagged that "small talk, speech terms (e.g. Mm-hmm, Very, etc.)" pass through uncaught.

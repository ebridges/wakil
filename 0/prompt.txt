## New, substantive problem: Step A's literal mechanism doesn't exist for this model

I checked the current Anthropic API behavior for extended thinking before accepting Step A as sound, since it's now the load-bearing first move in the sequenced plan. Two facts matter here, both directly checkable against `src/wakil/llm/client.py`:

1. `DEFAULT_ANTHROPIC_MODEL = "claude-opus-4-8"`, and `AnthropicClient.complete` unconditionally sends `thinking={"type": "adaptive"}` on every call.
2. On Opus 4.8 (and every other currently-served model this codebase could plausibly point at — Opus 4.7, Fable 5, Opus 5, Sonnet 5), **`thinking: {type: "enabled", budget_tokens: N}` is not a live option — it returns HTTP 400.** The `budget_tokens` mechanism is deprecated-and-still-functional only on Opus 4.6 and Sonnet 4.6, as a documented transitional escape hatch; it is fully removed everywhere else, including Opus 4.8.

Step A as written says: "check whether the Anthropic API supports capping the thinking budget explicitly (a fixed `budget_tokens` in place of adaptive mode) for this specific call, and rerun the original failing transcript against it." For `claude-opus-4-8`, this isn't an open empirical question to check — it's a known 400. Running that experiment doesn't produce a maybe; it produces an immediate, deterministic request failure, unrelated to the truncation bug being investigated. As written, the "try the direct fix first, before any batching machinery" step would burn a cycle hitting a wall that Anthropic's own API documentation already rules out.

This matters more than a wording nit because **the actual available lever is different and currently unused in this codebase**: `output_config.effort` (`low`/`medium`/`high`/`xhigh`/`max`), which does control thinking depth on Opus 4.8 and is fully compatible with `thinking: {type: "adaptive"}`. Right now `AnthropicClient.complete` never sets `output_config` at all, so the call runs at whatever Anthropic's server-side default is (documented elsewhere as `high` for this model family) — nobody has ever tried lowering it. That's a real, live, previously-unidentified variable this ADR should be testing and currently doesn't mention. There's a second real lever too: `thinking: {type: "disabled"}` is accepted outright on Opus 4.8 (no effort-level restriction, unlike Opus 5), which would eliminate the thinking-token cost entirely at the price of losing whatever quality adaptive thinking buys for the revision judgment.

**Concretely, Step A needs to be rewritten to say:** try `output_config={"effort": "medium"}` (or lower) as the primary lever, with `thinking: {type: "disabled"}` as a secondary experiment, both requiring a small `AnthropicClient.complete` signature change to accept and forward `effort`/thinking-mode — not "check whether budget_tokens capping is supported," which is a dead end already knowable without running anything. This is exactly the kind of thing your own Step A discipline is supposed to catch ("targets the variable the diagnosis actually blames") — as written it targets a variable that literally cannot be tuned on this model.

This doesn't undermine the sequencing logic itself (direct fix before batching machinery is still the right order), but it does mean the ADR's most concrete, ready-to-execute step is currently unexecutable as specified, and the actually-viable direct fix (`effort`) isn't in the document at all.

**#5 (Step B doesn't need a live-model eval) — I agree, you're right, I was overreaching.** The distinction you're drawing — bisection control flow is deterministic and testable with a scripted fake `ModelClient`, the way `complete_with_contract`'s existing retry logic already is, versus Decision 1's `relevance` field being a genuine model-judgment-calibration question — is a real and correct category distinction. **#8 (warnings-as-review is an existing pattern) — partial disagreement, worth stating plainly since you asked.** I agree it's not fair to make this ADR uniquely own fixing a pattern used elsewhere in the DAG, and I'm not asking you to. But I don't think "it's the existing contract" fully answers the underlying concern, because the *frequency profile* is different in a way that matters: the existing uses of `proposal.warnings` (missing target file, failed resolution call) are anomaly signals — they fire rarely, on genuine error conditions, so a user who sees one has reason to actually read it. The relevance-threshold warning this ADR introduces is not an anomaly — it's an expected, routine outcome of normal operation. Any `wakil enrich` run touching several tangential entities will emit "N entities left untouched below threshold" as standard output, every time. That's a much faster path to the warning becoming background noise a user learns to skim past, which is a real (if soft) erosion of the "human review" property CLAUDE.md cares about, even though the mechanism is technically unchanged. I don't think this blocks acceptance — it's not something this ADR needs to solve — but I'd rather it be named as a known, accepted UX risk in Consequences (one sentence: "this warning is expected to fire routinely, not exceptionally, and its long-term visibility to the user hasn't been validated") rather than settled by "it's the same contract as everywhere else," since the everywhere-else cases don't share this frequency property.

## 2. ADR 0008 in full detail

**Note on naming:** No ADR in this repo is titled "Porcelain CLI vs. skill-orchestration split." The closest and most relevant match to your description is **ADR 0008** — `docs/adr/0008-ingestion-decomposition-reject-multi-agent-mechanism.md` — "Decompose ingestion into classify/extract/resolve/enforce/finalize, reject the multi-agent mechanism." It's the ADR that explains why ingestion isn't one router-agent-driven command, which is functionally the same territory your description points at (why there's no single ingest+enrich+PR command — the split is between fixed, code-sequenced steps vs. agent-decided orchestration, not literally a "porcelain CLI" naming). If a differently-named doc exists elsewhere (e.g. in git history or an uncommitted draft), I did not find it under `docs/adr/`, `docs/`, `README.md`, or `CLAUDE.md`.

**Full text of ADR 0008:**

&gt; **Context.** `docs/ingestion-model.md` works through a concrete worked example — a GBrain/Obsidian vault whose ingestion is organized as a dozen cooperating Claude Code "skills" that an LLM agent reads and follows, with one agent classifying input and delegating to other agents for type-specific extraction. The document's central claim is that ingestion decomposes into five separable concerns regardless of how each one is executed: **classify** the input, **extract** type-specific structure, **resolve entities** against the existing knowledge base (shared across all source types), **enforce invariants** that gate every write, and **finalize** (commit). The document argues this decomposition is what keeps ingestion code from rotting into an `if kind == ...` ladder as source types grow, and that the benefit comes from not conflating the five concerns — not from how each one is executed.
&gt;
&gt; The document's "Where this meets wakil's principles" section addresses the worked example's *mechanism* directly: a router agent inferring content type and dispatching to other agents, each following its own markdown procedure, is exactly what `CLAUDE.md`'s Design Biases section lists under "Avoid" — "large agent frameworks," "multi-agent orchestration," and "overly abstract plugin architectures" — in favor of "explicit commands" and "small composable services." Importing that mechanism wholesale would violate wakil's stated design biases.
&gt;
&gt; **Decision.** Keep the five-concern decomposition (classify / extract / resolve entities / enforce invariants / finalize) but implement it as a fixed, code-sequenced DAG rather than agent-decided delegation:
&gt; - Classification stays an explicit CLI argument (`wakil ingest &lt;kind&gt; ...`), not content-inferred routing.
&gt; - Each extraction path pairs a mechanical function (fetch/parse/OCR, no model call) with a `wakil/skills/&lt;kind&gt;/SKILL.md` prose file (judgment only, no schema) that code loads and folds into a model call, validated against a shared `ExtractionOutput` Pydantic contract.
&gt; - Entity resolution is split out into its own always-invoked DAG node (not agent-remembered), producing `EntityResolution` results.
&gt; - Invariant enforcement (`validate_proposal()`) sits between `prepare_ingest`/`prepare_enrichment` and `apply_ingest`/`apply_enrichment` as one explicit step.
&gt; - Finalize is git-native (`--commit`/`--branch`/`--pr`), already implemented in `app/git_service.py`.
&gt;
&gt; This captures the worked example's real asset — accumulated, editable judgment per source kind — without adopting agent-decided control flow: **a step that must run, runs because code calls it, not because an agent remembered to.**
&gt;
&gt; **Consequences.**
&gt; - New source kinds (PDF, tweet, webhook capture) add a mechanical extractor and a prose skill file, not a longer `if/elif` branch or a bloated shared prompt.
&gt; - Entity-resolution bugs get fixed in one place instead of being re-implemented per source kind.
&gt; - The DAG's topology is never agent-decided, avoiding the class of failure the worked example's own skill docs guard against with repeated anti-pattern warnings (e.g. "a meeting is NOT fully ingested until enrich runs for every entity").
&gt; - wakil does not get an "adjacent maintenance" analogue (backlink repair, stale-page detection) yet; that remains a deliberately separate, lower-frequency command to build later.

Implementation: PR #9 (enrichment DAG, merged 2026-07-15), PR #13 (skill resolver wired into DAG, merged 2026-07-16), PR #14 (entity-revision DAG, schema page-shapes, merged 2026-07-18).

**Why this matters for the ingest/enrich split specifically:** the README and `docs/ingestion-model.md` establish that ingest is deliberately **two explicit steps** — `wakil ingest &lt;kind&gt;` (deterministic capture, one small title/abstract model call per ADR 0010) and `wakil enrich &lt;source-id&gt;` (the fixed two-model-call DAG: extraction, then always-invoked entity resolution) — rather than one combined command, because each step is its own code-sequenced, previewable, confirmable unit; a single "ingest+enrich+PR" command would collapse two independently reviewable checkpoints into one, and would reintroduce exactly the kind of implicit, agent-decided sequencing ADR 0008 rejects for reasons of predictability (every step runs because code calls it) and reviewability (each step previews before writing).

## 4. Human-in-the-loop / review gating mechanism

Yes — this is a first-class, repeatedly-cited mechanism, not just aspirational CLAUDE.md language. Key sources:

- **`CLAUDE.md`, "Working Agreement for Agents," items 11-12** — the exact lines you quoted: "Show reviewable diffs for knowledge-base modifications." / "Do not silently rewrite user knowledge." These are treated as binding design constraints and are cited by name in ADRs 0003, 0015, 0016, 0017, and in `docs/TROUBLESHOOTING.md`.
- **ADR 0003 (`docs/adr/0003-git-native-change-tracking.md`)** is the concrete mechanism: git branches + scoped commits (staged to *exactly* the files wakil wrote — never `git add -A`, so the user's own uncommitted work is structurally protected) + optional GitHub PRs via the `gh` CLI, as an alternative to direct working-tree writes. Notably, the ADR author states plainly: *"I could not find a document or transcript that lays out why git branches/commits/PRs were chosen over an alternative review mechanism (e.g., an in-app diff/approval queue, a database-only staged-changes table...). The choice appears to follow directly from the project's stated thesis and design biases... rather than a recorded comparison of alternatives."* So the git/PR flow is the review mechanism, but no ADR justifies it against alternatives from first principles — useful to know since MCP planning will need to decide whether to preserve the same PR-review checkpoint or design something else.
- **Command-level gating:** both `wakil ingest` and `wakil enrich` **preview before writing** (`--yes` skips the interactive confirm), and `validate_proposal()` runs as an explicit invariant-enforcement step between "prepare" and "apply" for every proposal (schema-validated frontmatter; a `type:` with no matching schema is a hard stop, never a best-guess write).
- **Entity resolution decisions** (create/update/skip) are always shown in the preview before anything is written (README, ADR 0008).
- **`docs/memory-model.md`** (lines ~250-270): frames the same shape generally — "The model proposes; the human decides; the result is a reviewable diff. This is the same shape as the current confirm-before-write flow" — and extends it conceptually to future memory-interference/reconsolidation features ("Reconsolidation as a reviewable proposal").
- **Follow-on evolution (still in-flight per ADR 0003):** PR #15 (open as of the ADR's writing) moves toward one branch/one PR per source across its whole capture→enrich lifecycle (rather than one per command invocation), records phase landings as PR *comments* (not body rewrites, to avoid clobbering manual edits), and fixes branches to always fork from the resolved default branch.
- **Practical enforcement example:** `docs/TROUBLESHOOTING.md` (line 154) cites the "never silently rewrite user knowledge" rule directly as the reason a heading-regex was loosened in code rather than bulk-editing existing notes to match — i.e., the rule is applied as an actual engineering tiebreaker, not just documentation.

This is the mechanism an MCP server will need to either preserve (tool calls that stop at "prepare"/preview and require a separate "apply" confirmation, or that always land on a branch/PR) or deliberately and visibly diverge from.
